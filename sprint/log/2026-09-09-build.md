A template is a Markdown file in `rapport/templates/`: front matter (`name`, `description`, `order`), body = the sections
the model is asked for. Five ship — meeting notes, interview, lecture or talk, sales call, journal — plus `custom`, which
carries the user's own prompt from settings. All of them are prefixed with `PREAMBLE`, the rules that always hold (write
in the language of the transcript, use the speaker names, never invent a fact). That preamble is verbatim the first
paragraph of the old fixed `SYSTEM` prompt, and `meeting.md` is verbatim the rest of it, so nothing changes for anyone
who does not touch the picker.

- `rapport/summarize.py` — loading, front-matter parsing, `build_system()`; `SYSTEM` is gone, replaced by `PREAMBLE` +
  a template body. `summarize()` takes an optional `Template`.
- `recordings.summary_template` — new column (migrated in `db.py`). The worker resolves the recording's own choice
  first, then the Settings default, then writes back which template produced the text.
- `GET /api/summary/templates`; `POST /api/recordings/{id}/summarize` takes an optional `{template}` and 400s on an
  unknown id without touching the stored one.
- Settings: `summary_template` (default "meeting") and `summary_custom_prompt`.
- UI: picker + Summarize/Regenerate in one header row in the Summary tab, with the template's description beside it and
  a dashed note when the summary on screen was written with a different template. Settings gets the default picker and,
  for `custom`, a prompt box. Details lists the template used. Cue Sheet tokens throughout, existing `Select`/`Textarea`.
- `desktop/sidecar/rapport-core.spec` copies `rapport/templates` into the frozen sidecar — the files are read from disk
  at runtime, so without this the templates would be missing from the DMG and every summary would fall back to the bare
  preamble. Worth remembering for anything else that reads a data file.
- Docs: `docs/how-it-works.md` (a table of what each template gives you) and `docs/developers.md` (how to add one).
