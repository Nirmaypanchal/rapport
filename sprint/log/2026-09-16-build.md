## Built 1: the ghost run — [#19](https://github.com/Nirmaypanchal/rapport/pull/19),
[#21](https://github.com/Nirmaypanchal/rapport/pull/21), [#23](https://github.com/Nirmaypanchal/rapport/pull/23),
[#24](https://github.com/Nirmaypanchal/rapport/pull/24)

**The item's acceptance criteria named a cause that was not the cause, and so did my first fix.** The board said a
bare `pull_request:` trigger starts a second run that the squash-merge kills three seconds later, and asked for a
job-level condition. That condition is in (#19) and is worth having — but it did not stop the red runs, and the
last log's own instruction is what found out why: *verify by watching the next auto-merge, not by reasoning about
the YAML.*

1. **#19 — the guard.** Each job in `ci.yml` runs unless the pull request's branch is one `push` already covered.
   It mirrors the push filter rather than naming the merge bot's branches, so a same-repo `fix/…` does not fall
   through the gap between the two triggers. `tests/test_ci_workflow.py` reads the expression out of the real file
   and *evaluates* it against made-up events (a push, our own pull request, a fork's, a `fix/…`) rather than
   asserting how it is spelled; its small evaluator raises on any operator it does not know. Three mutations were
   run to prove the tests catch them.
2. **The probe** — [#20](https://github.com/Nirmaypanchal/rapport/pull/20), an empty commit on `draft/ghost-probe`,
   opened by hand and closed unmerged. Its CI run concluded **`skipped` in one second**, three jobs guarded out. So
   the guard works — on a pull request that is allowed to run.
3. **#21 — the wait, which was the second wrong diagnosis.** #19's own merge still went red, and the timings said
   race: opened 03:12:12, merged 03:12:15, run created 03:12:15, dead at 03:12:17. So `scripts/sprint_merge.py`
   made the merge wait for that run to conclude first.
4. **What the wait actually printed** is what solved it: `go: the pull request's CI run has settled
   (action_required) after 6s`. **`action_required`** — the merge bot opens its pull requests with `GITHUB_TOKEN`,
   and GitHub does not run workflows for events that token creates. The run is blocked before it starts, with zero
   jobs, waiting for an approval nobody will give; deleting the branch is merely what turns it red. #22's run sat
   at `action_required` for six seconds and went red the instant the merge deleted the branch — **while my wait
   step had already finished**, which is what made it visible.
5. **#23 — delete the corpse.** Nothing in `ci.yml` can rescue a run that was never allowed to start, so the merge
   deletes it. Only a `pull_request` run for that exact commit, completed, not successful, **with zero jobs** — a
   run whose jobs were merely skipped lists all three (#20's did), so nothing that ran can be mistaken for a
   corpse. A run whose jobs cannot be counted is kept: never delete what you could not check. Nothing here may hold
   a merge, so a refused delete or a broken `gh` ends with the red run we already had.
6. **#24 — the docs paragraph #19 added was wrong** and is rewritten with the real mechanism.

**Verified on the real thing, which is the only verification this item accepts.** `sprint/ci-docs` merged under the
new workflow and its log reads: `the pull request's CI run has settled (action_required) after 6s` → `run
35052441507: deleted — action_required, no jobs, nothing ran`. That branch's history now holds exactly one run: the
green push run. Before the change, every auto-merge left a red one.

## Built 2: an `ask` tool for MCP — [#22](https://github.com/Nirmaypanchal/rapport/pull/22)

One call to `rapport.ask.ask()` on top of what `search` already does, so the answer, the citation numbers and every
fallback stay in one place. A missing model is a state, not an error: excerpts, `answer: null`, a `reason`, and a
note telling the client to answer from the excerpts itself. `_excerpt()` now shapes a moment for both tools, so an
`ask` source is a `search` hit plus its citation number — asserted against a real `search` hit, not by hand. The
provider comes from the library's own `settings.json`, read directly, because `Library()` creates folders and
rewrites the file it reads and this server must not change a library it is only serving.
