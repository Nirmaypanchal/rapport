## Built 1: `sprint-merge` fails loudly — [#25](https://github.com/Nirmaypanchal/rapport/pull/25)

The `|| true` after `gh pr create` is gone, and with it the shell logic around it. `sprint-merge.yml` is now three
one-line steps — `open-pr`, `prune-ghost-run`, `merge` — and every decision lives in `scripts/sprint_merge.py`
beside the pruning that was already there. Four things can no longer happen quietly:

1. **A failing `gh` call fails the step**, with what `gh` said in the log. That is the 2026-09-09 failure exactly:
   the "Allow GitHub Actions to create and approve pull requests" setting was off, `gh` said so and exited
   non-zero, and `|| true` reported success having merged nothing — twice.
2. **After creating a pull request it asks GitHub whether one exists.** Asked up to three times, three seconds
   apart, because a list that has not caught up would otherwise be a red job for nothing.
3. **Reaching the merge with no pull request is an error**, not an `exit 0`.
4. **The merge step lost its `if:`.** One step now decides for every CI conclusion — merge, comment on a red
   branch, hold a `needs-human` one — so "satisfied neither condition and went green" is not a reachable state.

A hold stays a decision rather than a failure: green job, the reason on stdout.

**Verified against real red and real green, which is what the item asked for.** Offline first: 28 new tests, and
three mutations to prove they bite (`|| true` put back on a step; a `needs-human` pull request merged anyway; the
ask-again check removed) — each failed exactly the test written for it. Then against the live GitHub API through a
read-only `gh` stand-in, since `gh` is not installed here: a real branch with no open pull request gives
`would open` in a dry run and a red `sprint-merge stopped: no open pull request to merge` without one; a refused
`gh pr create` exits 1 with the refusal in the log; `merge_plan` reads the real label arrays of #24 and #15.

Then on the real workflow, which is the only verification that counts — see below.

## Built 2: Ask streams its answer — [#26](https://github.com/Nirmaypanchal/rapport/pull/26)

The next item on the board, and also the branch that put the new merge workflow through both of its paths.

`summarize.stream_chat()` sits beside `chat()`, which is left alone: a summary is written in the worker and read
when it is finished, so only the call a person waits in front of gains anything. Ollama's `/api/chat` with
`"stream": true` (one JSON object per line, an unreadable line skipped rather than ending the answer); MLX's
`stream_generate` under the same lock `_mlx_chat` holds. `ask.ask_stream()` yields `{"delta": …}` and then exactly
one final event — and `ask()` was refactored to share `_prepare`, `_finish` and `_failed` with it, so the two
deliveries cannot disagree about what an answer is. A test asserts the final event equals `ask()` exactly.

`POST /api/ask` now answers `application/x-ndjson`. Two things that needed deciding rather than guessing:

- The empty-question **400 moved above the generator**. Once a streaming response has started, a status code can
  no longer be set, so an empty question would have looked like a successful answer to nothing.
- **A delta with newlines in it stays one line**, because `json.dumps` escapes them. There is a test for it: a
  bulleted answer is mostly newlines, and a raw one would split an event in two.

In the UI the blinking "Reading your transcripts…" now shows only until the first piece arrives, then the text
grows in the same answer card. Citations stay plain text while it writes and become buttons with the final event:
which excerpt `[2]` is depends on the finished source list.

**Where I went past the spec, deliberately:** the acceptance said `ask-panel.tsx` reads the stream with its own
`fetch`. The reading is in `lib/api.ts` as `askStream()` instead — every other fetch in the app lives there, and
the point of the instruction (do not reuse `api()`, which assumes one JSON body) is kept.
