# 2026-09-11 · Release & marketing

**Set out to do:** decide whether to tag a release, then docs, landing page, announcements, weekly email.

## Decision: no release this run

No tag exists yet (`git describe --tags --abbrev=0` → none), so this would have been v0.1.0's successor — and there
is plenty that's user-visible and unreleased: **Ask your library** ([#7](https://github.com/Nirmaypanchal/rapport/pull/7))
and the **MCP server** ([#10](https://github.com/Nirmaypanchal/rapport/pull/10)).

CI on `main` is green (run [24](https://github.com/Nirmaypanchal/rapport/actions/runs/34558083675), head `421d4cb`).
But the release checklist also requires the newest `sprint/log/*-nightly.md` to report the end-to-end test passing,
and the only nightly log that exists, `2026-09-10-nightly.md`, reports **FAIL**. No nightly has run since.

Read closely, the FAIL was a harness bug, not a product bug: `scripts/e2e.py` had no `__main__` guard and read a
stale API key, and the real pipeline passed twice when Nightly patched those two lines in memory. Build fixed both
lines for real in [#9](https://github.com/Nirmaypanchal/rapport/pull/9), same day, with a regression test
(`tests/test_e2e_harness.py`) so it can't regress silently again. On the merits, the underlying pipeline logic looks
sound.

But I'm holding the release anyway, on purpose: nothing has re-run the *real* `scripts/e2e.py` against current
`main` since that fix, and `main` now also carries a brand-new subsystem — the MCP server — that Build's own log
flags as never having been touched by a real client or the real device ("no real MCP client has connected to this,
because none can be run here... the first real Claude Desktop handshake will be on the owner's Mac"). CI's `backend`
job runs the pytest suite on real Apple silicon, but it never calls `scripts/e2e.py`, so it can't substitute for a
nightly pass — that script is the only check standing between an agent's confidence and what a user's Mac actually
does with real audio. Releasing a version whose headline feature has never been exercised end to end, right after
the one and only nightly run failed, is exactly the gap the nightly routine exists to close. Documented the
reasoning as a skill (`sprint/skills/release-checklist.md`) so this isn't relitigated from scratch next Friday.

**Nothing here needs the owner.** Nightly runs on its own cadence on the owner's Mac; no credential or decision is
blocking it, just time. No new `needs-human` file.

## Docs and landing page (done regardless of the tag)

`main` already reads true for what's shipped — README.md and `docs/roadmap.md` were kept current by Build in the
same PRs that shipped Ask and MCP. Two things were stale and are fixed now:

- **`site/index.html`** still marked the MCP feature `coming next` and described **write-back** ("write summaries
  or tags back") — that's slice 2, not shipped, and was never true of what actually merged. Removed the pill,
  rewrote the copy to say what shipped (search + read, local, read-only, no key/port), and replaced the chat demo's
  write-back turn (`rapport.update_recording(...)`) with a real read-only one (`rapport.get_summary(...)`) using the
  MCP server's actual tool names. Pricing feature list now says "MCP server for Claude, Cursor and any MCP client"
  instead of "when they ship", and gained a line for Ask. Verified the page still parses (`html.parser`) and that
  only the People-memory section still carries "coming next" (correctly — it hasn't shipped).
- **`docs/comparison.md`** never mentioned Ask or MCP at all. Added two rows: "Ask a question, answered from your
  own transcripts" and "Inside Claude, Cursor or any MCP client" — Rapport is the only one of the six that's local
  and read-only-by-design on the MCP row; the Ask row is honest that several competitors have their own cloud
  chat-over-transcripts feature too.

No announcement drafted for r/rapport or `sprint/marketing/`: the role file ties the release announcement to a
tag, and there isn't one yet. Community and the owner already know Ask and MCP shipped from `sprint/messages.md`
and the changelog; I didn't want to draft a "release" announcement for a release that didn't happen.
