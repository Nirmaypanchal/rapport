No open pull requests, CI green on `main` (run 18). But the **first nightly log had arrived and it was a FAIL**

The nightly's verdict was precise and correct: the product was healthy, `scripts/e2e.py` was not. Two bugs, both
mine to fix, both shipped as [#9](https://github.com/Nirmaypanchal/rapport/pull/9) (`9f6dd46`):

- **No `if __name__ == "__main__"`.** Running the script defined its functions and exited 0 printing nothing. Every
  caller saw a silent pass while testing nothing. This is the worst kind of bug a test harness can have, and it had
  been there since the harness was written — which is why nothing shipped since 0.1.0 had ever met the real pipeline.
- **A stale contract**: it read `ids["ids"]` from `POST /api/import/path`, which has answered `{"imported": [...]}`
  since the route was written.

Both fixed, plus the guards so the class cannot come back: `tests/test_e2e_harness.py` shells out to
`scripts/e2e.py --help` and asserts it prints its usage (a missing entry point prints nothing) and that the file
stays executable, and `tests/test_api.py` now pins the `imported` key — the one API contract the harness hard-codes.
The nightly suggested the first of those; it was the right suggestion.

Also worth saying plainly: **the nightly routine works, and it earned its place on day one.** It found a bug that
every Linux test and every CI run is structurally incapable of finding. My log yesterday said to escalate if no
nightly appeared; it appeared, so nothing was escalated.

## Built: MCP server, slice 1 — [#10](https://github.com/Nirmaypanchal/rapport/pull/10)

`rapport/mcp.py`. Claude Desktop, Cursor or anything else that speaks MCP can now read the user's library: six
read-only tools over stdio, no key, no port, no running app.

| Tool | Gives |
|---|---|
| `search` | the moments matching a question, each with the turn either side, recording id and timestamp |
| `list_recordings` | newest first, filtered by title or date |
| `get_recording` | title, date, length, source, who speaks and for how long |
| `get_transcript` | speaker-labelled turns, or a `from_sec`/`to_sec` window |
| `get_summary` | the summary Rapport wrote, as Markdown, with its template |
| `list_people` | everyone recognized, speaking time, last heard |

`list_recordings` is the one tool beyond the five the backlog asked for. Without it an assistant can only reach a
recording through words someone said inside it, so "what did I record on Tuesday" had no answer. The rest of the
acceptance criteria are met as written.

Four decisions, the first two now in `sprint/decisions.md`:

- **No SDK.** The stdio transport is JSON-RPC 2.0, one message per line, and a read-only tool server needs
  `initialize`, `tools/list`, `tools/call` and notifications — about 90 lines of standard library. The frozen bundle
  is already 1.3 GB with "make it smaller" on the backlog, so a dependency has to earn its place and this one would
  have bought plumbing we can read in one sitting. What it would also have bought and we now do not have: resources,
  prompts, sampling, progress, cancellation. If we want any of those, revisit the decision rather than hand-roll on.
- **Read-only, and tested as such.** No handler writes, and `test_no_tool_writes_to_the_library` snapshots every
  table, runs every tool, and compares. "User data is sacred" has to mean something when the caller is a model
  reading text off the internet.
- **SQLite directly, not the local HTTP API** — no port, no token, and it works with the app closed.
- **Retrieval was not written twice.** `search` is `rapport/ask.py` (keywords → `db.search(match="any")` →
  `pick_hits` → `passages`) in an MCP envelope, exactly as yesterday's note asked. Retrieval improves in one place.

Two more things worth knowing. `rapport-core --mcp` runs the same server from the installed app, so the Claude
Desktop snippet is two lines and needs no checkout — it starts no worker, no importer, no server. And an MCP client
gets the same "a missing thing is a state, not an error" treatment as Ask: no summary, no transcript yet, or an
empty window each come back with a `reason` and a sentence saying what to do instead; a truncated transcript names
the exact `from_sec` to ask for next; bad arguments come back as failed tool results the model can read and correct,
not protocol errors.

**`docs/privacy.md` needed a new section and a new table row, and this matters more than the feature.** Its promise
was "audio, transcripts, summaries and people never leave the machine". Connect a *cloud* assistant to this server
and what it reads goes to that assistant's servers, exactly as if you had pasted a transcript into the chat. That is
the first hole in the product's central claim, so it is now stated on the privacy page, in the setup instructions in
`docs/integrations.md`, and nowhere that a user could miss it. The claim is now: Rapport never sends your recordings
anywhere; the one way words can leave is a cloud assistant you connected yourself, and only what it reads.

**Verified:** `scripts/test-light.sh` — 81 passed, 27 new across the two branches. `npx tsc --noEmit` and
`npm run build` clean (no UI in this slice). Beyond the unit tests, the server was **driven for real over a pipe**
against a scratch library, both as `python -m rapport.mcp --library …` and as `python -m rapport.sidecar --mcp`:
initialize (with version negotiation), `tools/list`, and `tools/call` for search, get_recording, get_transcript,
get_summary and list_people all answered correctly, a bad argument came back as a readable tool error, and a missing
library exits 2 without creating an empty one. CI green on both branches; both squash-merged themselves.

**What is not verified:** no real MCP client has connected to this, because none can be run here. The protocol is
followed from the spec and exercised byte-for-byte over a pipe, but the first real Claude Desktop handshake will
happen on the owner's Mac. That is the single most useful thing the next nightly could add.
