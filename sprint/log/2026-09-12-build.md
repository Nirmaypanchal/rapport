**Built: file each escalation once** — [#11](https://github.com/Nirmaypanchal/rapport/pull/11), merged as `8bfca45`.

The old workflow asked the GitHub issue *search* index whether a request had already been filed
(`gh issue list --label needs-human --state all --search '"<title>" in:title'`). I pulled the job log from the run
that caused it (run 4, 2026-09-09 14:11): it skipped `actions-cannot-open-prs.md` correctly, because search found #2,
and then opened #6 for a file whose issue #3 had existed for two and a half hours. Same query shape, same age,
different answer — the search index is fuzzy and eventually consistent, and it is the wrong instrument for "does this
exist". Six-hourly cron meant every unresolved file was a recurring email to the owner.

- `scripts/needs_human_issues.py` now holds the decision. It asks `gh issue list --label needs-human --state all`
  (the list API: immediate, exact, no index in the way) and matches on a `<!-- needs-human-file: <name> -->` marker it
  writes into every issue body, so an edited title cannot open a second issue either. Issues opened before markers
  existed (#2, #3, #5, #6) still match on their exact title, so nothing already filed is re-filed.
- `--state all` is deliberate: the owner closes an issue when it is done and the *next* Research run moves the file to
  `done/`. Nothing may be re-filed in that gap.
- One file that cannot be filed no longer stops the rest, and the job goes red so the failure is visible.
- The workflow is now checkout plus one line. The logic is in `scripts/`, where `tests/test_needs_human.py` (20 tests)
  can reach it — including a replay of the #3/#6 regression and a guard that the workflow never goes back to `--search`.
- `docs/developers.md` describes the escalation path; dropped the stale "summary templates" contribution idea, which
  shipped in #1.

**Closed by hand**, as the item's acceptance asked: [#6](https://github.com/Nirmaypanchal/rapport/issues/6) as a
